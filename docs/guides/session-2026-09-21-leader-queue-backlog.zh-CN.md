> [`session-2026-09-18-team-provider-spend-block.zh-CN.md`](./session-2026-09-18-team-provider-spend-block.zh-CN.md)

## 一句话总结

用户装上带 09-18 修复的新版后反馈"问题没解决，队长还是挤压了好多消息"（176 条）。
**修复确实装上了，但这次是另一个根因**：`mark_idle` 在每个成员每轮结束时无条件往队长信箱
写一条，没有去重。两条改动：源头去重（`c7c9dc8`）+ 给存量用户一个出口（`72bb713`）。

## 一、同一个症状，三个根因（最重要的一节）

UI 上都长成「正在处理中……已排队 N 条」，但成因完全不同，**修了一个不会顺带修另一个**：

| # | 根因 | 现场特征 | 修复 |
| --- | --- | --- | --- |
| 1 | 陈旧信号把槽位卡在 `Queued`（`complete_signals` 全有全无） | 队列**不增长**，卡住不动 | 09-18，见前篇 §2.3 |
| 2 | 服务商因额度拒绝，调度器拿队列撞墙 + 失败通知反灌队长 | 会话里**满屏报错卡片**（`USER_LLM_PROVIDER_RATE_LIMITED`） | 09-18，见前篇 §3 |
| 3 | **闲置通知按成员活跃度无限增长** | **一个报错都没有**，队列稳步上涨 | 本篇 |

### 怎么快速区分

- **先看有没有报错卡片**。有 → 大概率是 #2；没有 → 看 #3。
- **问队长自己**。这次是队长把答案说出来的："The message queue is mostly idle
  notifications plus the substantive updates from 运维"。它能读自己的信箱，比外部推断准。
- **别用时间戳判断"修复装没装上"**，直接在二进制里搜那次修复的独有字符串：

  ```bash
  grep -c "provider refused on spend grounds" resources/bundled-dreamcore/win32-x64/dreamcore.exe
  ```

  本次就是先做了这一步排除掉"没装上"，才去找新根因的。

## 二、根因：`mark_idle` 每轮写一条，从不去重

`scheduler/state.rs` 的 `mark_idle`：

```
每个成员每一轮结束
  → event_loop 的 finalize_scheduler_turn
  → scheduler.finalize_turn(slot_id)
  → mark_idle(slot_id, None)
  → 无条件 mailbox.write(lead, IdleNotification, "idle")
```

`summary` 在 `finalize_turn` 这条路上恒为 `None`，所以内容就是**字面的 `"idle"`**。

于是队长的队列是按**成员的活跃程度**增长的，而不是按"有多少他能处理的事"。4 个成员干一
下午就是几百条。更贵的代价不是数字，是**它们把真实的成员汇报从队长的上下文里挤出去**。

`mirror_unread_to_conversation` 早就把这个类型整个跳过（不往会话里写），说明代码本身早就
认定它是噪音——但它照样占队列、照样进提示词。

### 修法（`c7c9dc8`）

同一槽位的未读闲置通知还挂着时，第二条不再写。队长消费掉之后下一轮照常通知。

**这跟 09-19 修的投递失败通知去重是同一形状的改动**——当时修了罕见的那个调用点
（`notify_leader_delivery_exhausted`），漏了最频繁的这个。以后再看到"给队长写通知"的代码，
先问一句：**它会不会按成员活跃度增长？**

唤醒逻辑**一个字没动**：`maybe_wake_leader_when_all_idle` 照常返回队长 id，队长每次 finish
都还是会被唤醒，只是不再每次攒一条信箱行。

### 碰倒了一个既有测试，没有弱化它

`s5_consecutive_finish_events_after_dedup_clear` 断言"两次 finish 产生 2 条闲置通知"。
看它自己的注释，这条测试的本意是**"第二次 finish 不能被 dedup 窗口吞掉"**，而那由两个
`wake target` 断言直接覆盖（都还过）。信箱条数只是个代理指标，恰好是本次故意改的行为，
所以改成钉死合并后的 1 条并写清了为什么。

> 按 AGENTS.md 的规矩：测试挂了先判断"断言是否仍代表正确行为"。这里属于"接口有意变更"，
> 可以改测试，但**新断言必须仍然验证有意义的行为**——不能松成 `assert!(count > 0)`。

## 三、存量用户的出口：停止清理 + 重新问询（`72bb713`）

源头去重管住新增，但**已经堆在那儿的 176 条不会自己消失**。查完确认：

- **点停止不清。** `pause_slot` 只碰 `slot.paused` 和 `slot.active`，队列一个不动；
  `cancel_batch` 走 `DeliveryOutcome::NotFailed`，消息退回未读。用户一发消息解除暂停，
  **全部回来**。这是故意设计的（配额暂停靠它保证"活儿一条不丢"），这里反过来咬人。
- **重启也不清。** 信箱行在 DB 里且未读，恢复扫描会重新捞出来。
- **唯一会清的 `cancel_run` 用户点不到**：`ipcBridge.team.cancelRun` 定义了，但渲染层
  **没有任何调用点**。

所以改成：**停止时丢掉该槽位队列里的闲置通知**。

**只丢这一个类型**——成员的真实汇报是 `Message`，一条不动（测试里特意把一条真实汇报混在
5 条闲置通知里，断言它必须活下来）。

### 丢东西就得交代，所以加了一轮问询

用户定的：清完之后队长要**主动问一圈**，免得漏掉。实现是往队长信箱塞一条 `Message`
（所以不会被自己的清理规则吃掉），内容让它 `team_send_message` 到 `"*"` 广播，请每个成员
重报最新状态。

两个刻意的细节：

- **没东西可丢时什么都不加**——不会每次点停止都无谓骚扰队长一轮，有测试钉死。
- **放在取消活跃批次之后**执行，因为那一轮已认领的行会退回未读，得一并算进去。

## 四、验证

- 两条都做了**回滚验证**：去重关掉 → 10 轮产生 10 条（修复后 1 条）；清理关掉 → 5 条闲置
  通知全留着。两次测试都立刻变红。
- `cargo nextest run -p dream-core-team`：**774 通过**，clippy 干净。
- ⚠️ **两条都要重新打包才生效**（`Cargo.lock` + bundled 二进制）。用户明确说下次一起打。

## 五、还没做

- **两条改动尚未打包发布**，存量用户手上仍是旧行为。
- 停止只清**被停的那个槽位**。理论上队长之外的槽位不会有闲置通知（只写给队长），所以等价
  于"清队长"，但如果以后闲置通知改成也发给别人，这里要重新想。
- `cancel_run` 依然没有任何 UI 入口。本次没动它——停止清理覆盖了实际需求，加入口是更大的
  产品决策。
