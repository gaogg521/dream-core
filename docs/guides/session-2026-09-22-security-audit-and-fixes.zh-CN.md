# dream 产品安全审计报告

日期:2026-09-21
范围:dream-ui(桌面客户端)、dream-core + dream-engine(核心引擎)、dream-en(企业管理后台)、dream-trial-broker(计费/试用代理服务)——即用户实际会用到的产品和服务本身,不含内部开发/构建环境。
方法:四路并行只读代码审计,每项结论均附文件路径+行号证据,未做渗透测试,不代表已发现全部问题。

## 一、结论先行

**没有发现能被远程直接利用、大规模窃取全体用户数据的"灾难级"漏洞。** 用户在正常使用产品的过程中,基础的加密、鉴权、隔离机制是起作用的。

但确实存在**几个真实的、会影响用户数据安全的具体问题**,主要集中在"本地明文存储"和"限流可被绕过"这两类。

---

## 二、用户在使用产品时,数据是怎么被保护的

### 2.1 产品视角——这对用户意味着什么

- **数据默认留在用户自己的设备/企业自己的服务器上**:用户的对话记录、技能配置、MCP 连接信息,默认存在用户自己的电脑本地,或者企业客户自己部署的服务器上,不会被强制先上传到我们的云端才能用。这是真实的架构事实,对重视数据不出内网的企业客户是有说服力的。
- **有风险的操作,用户始终知情且能拦下来**:AI 帮用户执行命令、改文件、联网抓取这类会产生实际后果的动作,默认都要用户自己在界面上点确认才会真的执行,不是"AI 说了算,用户后知后觉"。这保证了用户对自己数据/设备的最终控制权。
- **企业用户能管住自己的边界**:企业管理员能看审计日志、能限制员工能用哪些模型渠道、能对外发的内容做敏感信息扫描,员工的身份统一走 SSO 管理——这些是企业用户保护自己组织数据不外泄的实际手段,底层的权限隔离目前是"不确定归属就拒绝"而不是"不确定就放行"。
- **一个需要注意的地方**:目前"本地数据都加密保存"这件事对用户来说是**部分兑现**——用户填的第三方模型密钥、账号安全相关的密钥做了加密,但用户添加的 MCP 工具配置、聊天记录本身目前是明文存在本地文件里的。也就是说,如果用户自己的电脑中了木马或者被人拿到设备,聊天记录和部分工具配置是可以被直接读出来的,不是所有本地数据都上了锁。这个现状应该让用户知道,而不是笼统地讲"你的数据都是加密的"。

### 2.2 技术视角——具体是怎么做到的

- **关键凭证加密**:用户填的第三方模型 API Key、身份验证相关的密钥(如 MFA),统一用 AES-256-GCM 加密后才存到本地/服务端数据库。
- **密码不会被还原**:管理后台的账号密码用 bcrypt 单向哈希存储,加了防"猜密码时靠响应速度反推谁存在"的保护;系统自动生成的初始密码是随机 16 位强密码,而且首次登录强制要求用户改密,不存在所有人共用同一个默认密码这种情况。
- **风险操作需要用户确认**:执行命令、写文件这类操作默认要弹窗等用户确认;企业版还有一层额外的安全策略检查,这层检查一旦因为异常查不到该按什么规则处理,会选择**拒绝执行**而不是"查不到就先放行",避免因为系统抖动变成不设防状态。
- **登录状态有正规的失效机制**:用户的登录令牌是签名过的,不能被伪造;支持强制下线(比如改密后旧登录状态立刻失效)。
- **企业内的数据不会串到别的企业**:企业管理后台的接口都是按"这个人属于哪个企业"来过滤数据的,不是客户端说自己是谁就信谁;查不到用户归属哪个企业时,现在是拒绝其访问管理功能,而不是当作普通用户处理。
- **软件更新是可信的**:客户端自动更新走加密连接,且会校验安装包的完整性签名,同时防止被诱导装回旧版本(旧版本可能带着已经修复的漏洞)。
- **用户主动上传的诊断信息会脱敏**:用户遇到问题上传反馈时,系统会先过滤掉里面的敏感字段;企业版还有敏感内容扫描,防止内部信息被无意带出企业边界。

## 三、真实存在、会影响用户数据安全的问题

### 高优先级

**1. "记住密码"存的是可以被还原的明文,不是真加密**
- 用户勾选"记住密码"登录时,密码会用一种很容易被逆向的方式(简单编码 + 字符串反转)存在本地。
- **对用户的实际影响**:如果用户的电脑中了木马,或者被别人拿到设备,存下来的密码可以被一步还原成明文,进而登录用户的账号、看到用户的所有数据。
- **修复对用户的影响**:改成用操作系统自带的安全存储(Windows/macOS 都有)之后,对用户来说体验完全不变,登录、记住密码的操作方式不会有任何变化,也不需要用户重新登录一次——只是背后存储方式变安全了。

**2. 试用/计费服务的限流可以被伪造身份绕过**
- 我们对外提供的试用额度/托管搜索服务,是靠"这个 IP 一小时最多用几次"来防止被刷的,但这个判断依据可以被访问者简单伪造,导致限流形同虚设。
- **对用户的实际影响**:这不直接泄露某个用户的数据,但会被人恶意刷走本来该分给正常用户的免费额度,长期看会影响正常用户能分到的服务资源,也会增加我们的运营成本(有每日预算硬顶兜底,不会无限失控)。
- **修复对用户的影响**:对正常使用的用户几乎无感——除非用户本来就是和很多人共用同一个网络出口(比如公司内网),修复后如果限流规则没调好,理论上存在一起被误判为"同一个人在刷"的小概率场景,需要我们上线后观察一段时间来确认没有误伤。

**3. 用户添加的 MCP 工具配置和授权令牌是明文存的**
- 前面提到"部分兑现"的加密问题具体就是这项:用户配置的 MCP 工具(比如连接自己的其他系统、其他账号的授权信息)目前是明文存在本地,而不是像模型密钥那样加密。
- **对用户的实际影响**:如果用户的电脑数据被别人拿到,这部分授权信息可以直接被拿去用,风险和第 1 条类似,只是针对的是"用户接入的第三方工具"而不是"登录密码"。
- **修复对用户的影响**:对用户来说完全无感——这是纯后台存储格式的改动,用户已经配置好的 MCP 工具在升级后照常工作,不需要用户重新配置或重新授权一次。

**4. 独立命令行工具的账号凭证明文存储且没锁文件权限**
- 除了桌面客户端,我们还有一个可以独立使用的命令行工具,它把用户的登录凭证明文存在本地配置文件里,而且没有把这个文件设成"只有自己能读"。
- **对用户的实际影响**:如果这台电脑是多人共用的(比如公司的共享服务器),同一台电脑上的其他账号理论上能读到这个文件,进而拿到该用户的登录凭证。
- **修复对用户的影响**:对用户无感,纯粹是把文件权限收紧,不改变工具的使用方式。

### 中低优先级

| 问题 | 对用户的实际影响 | 修复是否会影响用户使用 |
|---|---|---|
| 加密密钥和被加密的数据存在同一个文件里 | 如果整个数据文件被人拿到(比如电脑被整体控制、云备份账号被盗),现有的加密防护效果会打折扣——因为钥匙和保险箱在一起 | 这项修复涉及更换密钥的来源方式,做得好可以让用户无感,但需要谨慎设计,尤其要保证"换电脑后用备份文件恢复数据"这个用户功能不受影响,不建议匆忙上线 |
| 聊天记录本身没有额外加密 | 电脑被物理接触或被恶意软件读取时,聊天内容可以被直接看到 | 视具体加密方案而定,做得好应该对用户无感 |
| 我们的服务在转发用户请求时,没有限制目标地址不能指向内部网络 | 主要是我们服务端自身被滥用的风险,不直接针对某个用户的数据 | **需要特别小心**:用户目前可以配置本地运行的模型(比如常见的本地 AI 模型工具,默认地址就是 `localhost`)作为自己的模型来源,这是一个真实存在、用户在用的功能。如果修复时无差别拦截所有"内网/本地"地址,会直接让这个功能用不了。正确做法必须把"用户自己主动配置的地址"和"系统内部动态抓取的地址"区分开,只拦后者 |
| 客户端渲染内容没有额外的安全策略限制 | 降低了"如果客户端某处出现网页安全漏洞"时的连带影响范围,属于纵深防御,不是当前已发生的问题 | 需要充分测试,避免误挡正常的图片、字体、流式内容加载,不能一次性收得过紧 |
| 用户导入 MCP 工具配置时,没有明确提示"这会在你电脑上执行命令" | 如果用户复制粘贴了别人分享的、带有恶意命令的配置,可能在不知情的情况下执行到本机 | 加一个确认提示,对用户来说只是多一次点击确认,不影响正常使用 |
| 管理后台用户自己设置密码时,规则要求偏松 | 用户设置弱密码后,账号被暴力破解的门槛更低 | 只影响用户以后"设置/修改密码"这个动作的规则,不会强制现有用户马上改密码,不影响现有登录 |

## 五、总结

**用户日常使用产品时,基础的数据保护是在起作用的**——密钥类信息加密、密码不可逆、风险操作要确认、企业数据不会串户、软件更新可信。

**但确实有几处会实际影响用户数据安全的问题需要修**,其中"记住密码是假加密"和"MCP 授权信息明文存储"这两条直接关系到用户自己设备被入侵时的损失大小,建议优先处理;"限流可被绕过"关系到公平使用和成本控制;这几项修复对用户的实际使用体验**都不会有负面影响**,大多数情况下用户完全无感。

唯一需要格外小心的是**限制内部网络访问**这一条——因为用户确实在用"连接本地运行的模型"这个功能,修复时如果处理不好边界,会误伤这个真实功能,这一项需要先想清楚再动手,不能图快。
