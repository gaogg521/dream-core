# 知识库与 Embedding 检索性能优化

日期：2026-10-22。范围：`dream-domain-devops`（检索、列表、筛选、单篇读取、建索引）。

## 结论先看

真实二进制端到端对比：同一份库（1500 篇、45 000 分块、384 维），个人版 `--local`，查询向量由随包的本地 ONNX 模型实时计算，全部经 HTTP 接口测量（脚本在会话 scratchpad，见文末）。

| 操作 | 旧（0.1.93 系） | 新 |
|---|---|---|
| 检索·自然语言新问题（中位数） | 1518 ms | 43 ms |
| 检索·精确编号 | 1149 ms | 29 ms |
| 文档列表 | 91 ms | 34 ms |
| 标题/正文筛选「复盘」 | 199 ms | 92 ms |
| 打开文档（读正文） | 69 ms | 12 ms |
| 自动建索引一篇 300 节文档（316 块，本地模型） | 71.3 s | 43.8 s |
| **建索引进行中的检索**（中位数） | **2026 ms，且只有关键词结果** | **40 ms，语义结果** |
| 建索引刚结束的检索 | 1174 ms | 56 ms |
| 首次检索（模型初始化 + 索引加载） | 2.0 s | 2.2 s（启动 20 秒后的预热会提前做掉） |

服务层基准（release，`rag_perf_bench`，同规模，embedding 用本机假服务）：检索 ~340 ms → ~10 ms（管理员与成员相同）；列表 45 ms → 8 ms；单篇可见性 43 ms → 0.2 ms；121 万字的大文档建索引从**直接失败**变为 1579 块、约 0.6 s。

## 找到的问题与改法

1. **每次检索读出全部分块的正文和向量**（45 000 块约 70 MB）再逐个算余弦。
   → 新模块 `vector_index.rs`：向量常驻内存、量化为 `i8`（45 000×384 约 17 MB），内存里粗排，只把前若干个候选（和关键词命中）从 SQLite 取回、用原始向量精确重算——调用方看到并据以设阈值的仍是精确余弦；权限仍由 SQL 算出的可见文档集合决定。
   一致性：`one_rag_chunks` 上的触发器把每次增删改的文档 id 写进 `one_rag_chunk_changes`，检索前按游标增量重载；日志被裁掉或数据库回退则全量重载。所以本服务之外的写入（备份恢复、其他进程）也能跟上（有测试）。MySQL 部署不使用（走原路径）。
2. **成员的权限条件让 SQLite 退化成扫描**：取候选时重复带上含子查询的 OR 条件，被规划成扫描所有可见文档的全部分块（成员检索 ~130 ms）。→ 候选只按分块 id 取，再用前一步按同一条件算出的可见集合在 Rust 里严格过滤。
3. **列表和权限判断读遍所有正文**：`visibility`、`library_id`、`content_revision` 是后加的列，物理上排在 `content` 之后，读它们要穿过每篇正文的溢出页。→ 迁移 022：三个覆盖索引（管理员列表、成员条件、按 id 关联），并删除被完全覆盖的旧 `(scope, team_id)` 索引。查询计划已确认走 `COVERING INDEX`。
4. **打开/下载/上传一篇文档要先列出全部文档**来判断可见性。→ `rag_document_visible`（与列表同一策略，逐查询条件对齐；有“每个查看者 × 每篇文档与列表一致”的测试）和 `rag_document`。
5. **大文档一次把所有分块塞进一个 embedding 请求**：请求体过大或超过服务商的条数上限就整篇失败。→ 远端每批 32 条、4 批并发；服务端以 400/413/422 或中途断开表示“太大”时自动对半拆分重试（连接失败、超时、5xx 不拆，避免放大请求量）。
6. **本地模型一把锁锁住整篇文档**：建索引期间所有检索的查询向量都要排队，2 秒预算一到就退回关键词。→ 每次持锁只处理 4 块；推理线程从固定 2 改为核数的 1/4（2–4，可用 `DREAM_LOCAL_EMBEDDING_THREADS` 覆盖）。实测 96 块：2 线程 5.2 块/秒、查询等 1009 ms；默认（4 线程）7.3 块/秒、查询等约 490 ms。
7. **筛选对每篇正文做 `LOWER()` 复制**。→ 改用 `LIKE … ESCAPE '!'`（SQLite 的 `LOWER` 本来就只折叠 ASCII，`LIKE` 语义一致），不再复制。曾试过走 trigram 全文索引，但它只在启动时为空才重建、外部写入的分块不会进去，会漏结果（被现有测试抓到），已放弃。
8. 关键词索引写入合并为一个事务（原来每块一次自动提交）。

## 已知的、这次没做的

- **本地模型每块约 512 token**：分块是 800 字，中文基本每块都到模型上限，这是建索引慢的主因（每秒个位数）。为本地模型改用更小的分块（例如 200–300 字）会更快、对 MiniLM 这类短文本模型的检索质量也可能更好，但会改变已建索引的形态、需要重建，单独评估。
- 手动“重新处理”与自动建索引同时针对同一篇时会重复嵌入，没有去重。
- 首次检索仍需 ~2 秒（模型初始化 + 索引加载）；已放进启动预热，若用户在启动 20 秒内就检索仍会碰到。
- 内存：向量索引约 每块 `维度` 字节（384 维 45 000 块约 17 MB；1024 维 10 万块约 100 MB）。
