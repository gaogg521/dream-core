# 周报生成器（Weekly Report Generator）

把零散的工作记录（待办、聊天、日历、会议、口头描述）一键整理成**结构化、可量化、可直接发送**的周报 / 日报 / 月报。

## 何时使用

当用户出现以下意图时触发本技能：

- 写周报、写日报、写月报、工作总结、工作汇报、汇报材料、述职
- 「帮我把这周的事整理成周报」「根据我的记录生成日报」「我要给老板发周报了」
- 用户粘贴了一堆零散记录（待办清单、聊天截图文字、会议纪要、日历事件）想让其成文

## 核心原则（务必遵守）

1. **先问一轮，别过度追问**：信息不足时，最多一次性问清 3 件事——时间范围、角色/风格、发给谁。用户说「随便/你定」时，默认「本周 + 通用风格 + 发给直属上级」，直接开写，不要反复确认。
2. **结构化**：所有内容归入标准骨架（见下），不写流水账。
3. **量化与动词开头**：每条成果用「动词 + 对象 + 结果/数据」表达，去掉「进行了、开展了、负责了」这类空动词。
4. **去 AI 味**：不用「赋能、抓手、闭环、颗粒度」等黑话；不写「综上所述」；句子短，像人写的。
5. **诚实**：用户没提供的信息不编造，用「待补充」占位并提示用户填。

## 工作流程

### 第 1 步：收集信息

一次问清（可合并成一句话）：

- **时间范围**：本周 / 今日 / 本月 / 自定义区间？
- **角色与风格**：技术 / 产品 / 销售 / 运营 / 通用？详见 `@references/weekly-templates.md`
- **发给谁**：直属上级 / 团队 / 客户 / 自己留存？（决定详略和语气）

随后请用户粘贴素材（待办、聊天记录、日历、会议纪要、Git 提交等），或直接口述。

### 第 2 步：归类整理

把素材拆解、去重、合并，逐条归入标准结构，剔除与工作无关的内容。

### 第 3 步：量化与提炼

- 把「做了 XX」改写成「完成 XX，覆盖 N 个场景 / 提升 M% / 交付 Z 个」。
- 提炼出 2–4 个「本周亮点」，放在最前面。
- 问题与风险要写清「影响 + 需要的支持」。

### 第 4 步：输出

- **默认输出 Markdown**（可直接粘贴到企微/飞书/邮件/语雀）。
- 用户要求美观版时，生成单文件 HTML（参考 `templates/report.html` 的结构与配色，内联 CSS）。
- 用户要求 Word 时，优先转 .docx 交付。

## 周报标准结构（通用）

```markdown
## 本周概览
一句话总结本周整体进展（做了什么、结果如何）。

## 本周亮点
- 亮点 1（带数据）
- 亮点 2

## 本周完成
- 【分类】完成事项：结果/数据
- ...

## 数据指标（如适用）
| 指标 | 本周 | 环比 | 说明 |
|---|---|---|---|

## 问题与风险
- 问题 1：影响 + 需要的支持
- ...

## 下周计划
- 【优先级】计划事项：预期结果
- ...

## 需要的支持
- ...
```

## 日报标准结构

```markdown
## 今日完成
- 事项：结果/数据

## 今日问题
- 问题：影响 + 解决进展

## 明日计划
- 计划事项：预期结果

## 备注
- 其他需要同步的信息
```

## 写作规范

详见 `@references/style-guide.md`，核心要点：

- 每条一条，用动词开头，控制在 1–2 行。
- 能用数字就不用形容词。
- 分点 ≤ 6 条；超过则合并同类项。
- 语气客观、不邀功、不甩锅。

## 风格模板

- 技术周报、产品周报、销售周报、运营周报、管理者周报：见 `@references/weekly-templates.md`
- 日报各场景模板：见 `@references/daily-templates.md`

## 输出格式

- Markdown：默认，通用性最强。
- HTML：单文件、内联 CSS、响应式，参考 `templates/report.html`。
- Word：用户明确要求时转换交付。

## 边界

- 不编造业绩数据；缺失处标注「待补充」。
- 不替用户对他人做负面评价；问题描述聚焦事实与影响。
- 涉及保密内容不写入周报，必要时提醒用户脱敏。
