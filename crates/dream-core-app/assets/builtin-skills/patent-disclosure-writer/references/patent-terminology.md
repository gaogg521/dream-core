# 技术抽象与专利用语

仅在输入含源码、接口文档、数据库结构或高度项目化表达时读取。本参考用于去除项目专属标识，同时保留可实施性所需的技术细节。

## 转译的目标

转译不是把所有内容替换成“模块”或“配置为”，而是把实现映射为稳定的技术概念：处理对象、触发条件、执行主体、处理规则、数据关系、输出结果和技术效果。

| 原始表达 | 推荐的技术表达 | 必须保留的信息 |
|---|---|---|
| `req_timeout = 3000` | 预设响应超时阈值；在一实施例中为 3000 ms | 单位、适用阶段、超时后的动作 |
| `max_retry` | 最大重试次数 | 计数起点、停止条件、退避规则 |
| `validate_user()` | 对请求主体执行身份凭证验证 | 凭证类型、验证依据、失败处理 |
| `if score > T` | 将特征评分与判定阈值比较，并根据比较结果选择处理分支 | 分数来源、阈值来源、两个分支 |
| `for item in queue` | 按预定顺序对任务队列中的待处理项执行迭代处理 | 顺序规则、并发方式、终止条件 |
| REST 接口调用 | 第一处理节点向第二处理节点发送包含目标数据的处理请求 | 请求内容、响应内容、失败/重试机制 |
| 数据库表和字段名 | 用于存储某类对象及其属性的结构化数据集合 | 主体关系、索引/约束中有技术意义的部分 |
| 模型推理函数 | 将场景数据输入目标模型，获得与技术任务对应的推理结果 | 输入定义、输出定义、预处理、模型关键结构 |

## 句式选择

- 方法步骤：`获取……；基于……确定……；响应于……执行……；输出……。`
- 装置或系统：`包括……；所述……用于……；所述 A 与所述 B 通信连接/数据关联。`
- 条件关系：`当……满足预设条件时……；否则……。`
- 参数范围：`参数 P 位于 [a,b]，其中下限用于……，上限用于……。`
- 技术效果：`由于特征 X 改变了机制 Y，因此在条件 Z 下减少/提高……。`

“配置为”只说明功能归属，不能代替实现机制。连续出现多个“用于……”但没有数据或结构关系时，通常属于过度功能化，需要补写操作、条件或连接关系。

## 抽象层级

同一核心方案通常保留三层表达：

1. **上位概念**：覆盖合理替代实现，如“状态特征”而非某个内部字段名；
2. **必要机制**：形成技术贡献的关系、顺序或计算；
3. **实施例细节**：具体协议、阈值、模型、材料或器件，用于证明可以实施。

不能为了扩大范围而删掉使方案成立的必要机制。也不要把单一实现无依据地概括为所有同类技术；上位概括必须有至少一种合理替代支持。

## 代码材料的处理边界

- 交底书正文通常不复制源代码，但可写伪代码、流程、公式、状态机或数据结构说明，只要它们有助于公开技术机制。
- 不写仓库路径、环境变量名、密钥、客户标识、内部域名、个人数据或许可证不允许披露的第三方代码。
- 区分业务目标与技术问题。例如“提高转化率”是业务目标；“减少终端与服务器之间的无效数据传输”才可能构成可验证的技术问题。
- 对 AI/算法方案，至少说明场景数据含义、输入输出关联、关键预处理、模型或算法如何参与技术过程，以及获得的技术效果。涉及模型训练时，根据方案贡献补充模块/层级/连接关系、训练步骤、样本构造、损失或关键参数。

## 自主补充的表达

用户只给出功能目标时，可以主动设计技术机制，不需要先询问。写作时区分：

- 用户材料已有的实现，使用客观陈述；
- 技能自主增加的算法、结构、控制关系或实施方式，作为“本次创造性补充”纳入方案；
- 尚未实验的参数范围和技术效果，使用“建议”“可通过……验证”或“在一候选实施方式中”，不得写成既有实测结论。

创造性补充不能只是换成专利句式。每项补充都应具有明确输入、处理机制、约束、输出和可测效果，并与至少一个实施例对应。

## 避免的表达

- 无证据的绝对词：`完全避免`、`必然提高`、`行业首创`、`显著领先`；
- 无机制的黑箱词：`智能处理`、`自动优化`、`高效算法`；
- 把结果当手段：`通过提高准确率来提高准确率`；
- 把未验证方案写成既成事实；
- 为了“专利腔”堆叠同义词或人为拉长句子。
