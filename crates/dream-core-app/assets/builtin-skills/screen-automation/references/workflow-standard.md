# 自动化流程开发标准（流程语言 v2）

本文是“屏幕自动化工程师”创建、修改和修复流程时必须遵守的当前标准。实际平台能力仍以
`cli capabilities` 返回值为准。

Windows 先执行 `$AppCli = & .\scripts\workflow_dev.ps1 -Action cli-path`，macOS 先执行
`APP_CLI="$(bash ./scripts/workflow_dev.sh cli-path)"`；后续示例中的 CLI 命令均调用该原生路径。

## 新流程包

```text
my-workflow/
├── workflow.md
├── workflow.py   # 可选：仅复杂流程使用
├── assets/       # 可选
├── tests/        # 可选
└── README.md     # 可选
```

`workflow.md` 是用户可读规则和步骤的主要来源。只有重复列表、复杂分类、多窗口关联等无法用标准
命令直接表达的流程，才可以增加一个根目录 `workflow.py`。不得创建 `workflow.json`、
`__pycache__`、`*.pyc`、日志、结果、调试截图或编译缓存。旧版 JSON/Python 包只能迁移，不能作为
新流程模板。

## 先选择包结构

只要标准命令能够完整表达，就只创建 `workflow.md`。满足下列任一条件时才增加 `workflow.py`：

- 需要遍历动态数量的可见列表项；
- 需要组合 OCR、颜色、轮廓或多个窗口证据进行业务分类；
- 需要维护流程自己的历史去重或逐项生成对象结果；
- 有限条件与重复语法仍无法清楚表达，但所需底层能力已经由 `ctx` SDK 提供。

“步骤多”“代码写起来方便”不是增加程序扩展的理由。程序扩展只能调用 `ctx`，不能导入
`pyautogui`、`cv2`、窗口系统 API、网络下载或命令执行模块。

## 文件骨架

```markdown
<!-- 屏幕自动化流程语言：2 -->

# 流程名称

## 基本信息

- 标识：my-workflow
- 版本：2.0.0
- 用途：一句话说明结果
- 目标系统：Windows、macOS
- 权限：读取屏幕、点击屏幕
- 引擎能力：browser-enhancement@1  # 仅使用浏览器增强时声明
- 创建者：本平台

## 参数

- 最长等待：DURATION(10s)
- 操作按钮：POINT(x=720,y=520)
- 内容区域：RECT(left=20,top=60,right=780,bottom=560)

## 启动窗口

- 标题包含：目标标题
- 首选进程：目标进程.exe
- 找不到时：提示用户重新选择

## 坐标与区域

- 区域【内容】：操作区域【启动窗口】内 参数【内容区域】
- 点【按钮】：操作区域【启动窗口】内 参数【操作按钮】

## 流程

### 1. 执行操作

- 在：操作区域【启动窗口】
- 观察：区域【内容】出现文字【操作前标志】
- 动作：点击 点【按钮】
- 验证：区域【内容】出现文字【操作后标志】
- 成功：完成
- 失败：等待 1 秒；重试 2 次；仍不能确认则停止
```

必需章节：基本信息、启动窗口、坐标与区域、流程。可选章节：参数、规则、交互模板、
程序扩展、输出。除这九个章节以外的标题都会被流程语言拒绝。标识使用 3–64 位小写字母、数字和
连字符；版本使用语义化版本。创建者写当前真实 Agent 产品名，不得猜测用户账号。

## 坐标和窗口

- `POINT(x=,y=)` 是点；`RECT(left=,top=,right=,bottom=)` 是区域。正文坐标永远相对于当前操作区域左上角；绝对屏幕坐标不得持久化。
- 启动窗口只是第一个操作区域。新窗口使用：
  `新窗口：等待新出现的窗口，标题包含【文字】，登记为操作区域【名称】`。
- 启动时按标题、首选进程筛选：唯一候选自动确认；多个候选显示多个虚线框让用户选择；没有候选则等待或按“找不到时”停止。不得猜测前台窗口、同名窗口或 Agent 窗口。

## 统一数字类型

禁止在新流程中使用裸 `[]` 数字列表、`RATIO` 或 `RATIO_RECT`。字段中文名描述业务，数据类型用英文构造器或自描述裸值表达：

| 写法 | 裸值写法 | 含义 |
|---|---|---|
| `POINT(x=,y=)` / `RECT(left=,top=,right=,bottom=)` | 不支持 | 操作区域内的相对像素点/矩形 |
| `PIXELS(n)`、`COUNT(n)`、`SCROLL(n)`、`DURATION(1.5s)` | `90`、`30`、`-600`、`1.5s`（上下文明确时） | 像素、数量、滚动量、时长 |
| `PERCENT(40%)` | `40%` | 百分比；流程源码必须带 `%` |
| `PERCENT_RECT(left=0%,top=50%,right=100%,bottom=100%)` | 不支持 | 操作区域比例矩形 |
| `HSV(h,s,v)`、`HSV_RANGE(lower=...,upper=...)` | 不支持 | HSV 颜色与范围 |
| `SIZE_RANGE(width=42..68,height=42..68)`、`AREA_RANGE(40..600)`、`RANGE(0.72..1.35)` | 不支持 | 尺寸、面积与普通数值范围 |

`1.5s`、`800ms`、`40%`、`true`/`false` 自描述类型，可直接写；无单位的裸数字只在
字段上下文已知时使用，例如 `最多处理次数：30`、`在 点【名称】滚动 -600`。`SCROLL` 的数值
表示屏幕像素的滚动量，通常使用数百像素；不要使用 `9000` 这类远超单屏范围的值。纵向滚动中正值向上、负值向下；横向滚动中正值向右、负值向左。

动态列表行只使用 `ROW_Y`，表示当前识别到的列表行 Y 基线；没有 `ROW_CENTER_X`。比例、锚点和偏移属于规则或参数，不能藏进程序扩展。


`在 点【名称】滚动 -600`、`在 点【名称】横向滚动 600`、`等待 2s`。

一个步骤只放一个动作。改变外部状态的动作必须同时有观察和验证。文字定位不唯一、不确定或
验证失败时不得盲点。

### 浏览器增强

浏览器增强是应用增强，不是执行者。步骤仍由 `engine` 执行，流程必须声明
`引擎能力：browser-enhancement@1`。Windows 可写 Chrome 或 Edge；macOS 当前只可写 Chrome。
每个流程打开独立受管会话，并在结束或失败清理时关闭；不得把用户日常浏览器 Profile 当作操作对象。

典型顺序是：打开会话 → 导航 → 定位并保存对象变量 → 读取或操作对象 → 验证可见结果 → 关闭会话。
定位要求唯一目标；零个或多个匹配都必须停止或进入有界恢复。下载只能保存到本次运行的受管下载
目录，流程不能指定任意系统目录。浏览器对象只在创建它的当前会话有效，不得跨会话复用。

程序扩展需要浏览器原子能力时，只能调用当前 SDK 的 `ctx.browser`：`open`、`navigate`、`locate`、
`find`、`read`、`click`、`fill`、`scroll`、`press`、`download`、`verify` 和 `close`。调用方法必须与
声明权限一致；所有改变页面的调用仍放入 `ctx.step.perform()` 或受监督的 `ctx.debug.step()`，
并在 `finally` 或流程清理阶段关闭本流程打开的会话。不得直接导入 Playwright、浏览器驱动或网络库。

创建包含 `browser-enhancement@1` 或 `agent-checkpoint@1` 的流程前，先以当前 `cli capabilities` 和
小助手设置中的组件/Agent 状态确认扩展能力可用。未启用、未授权或需要能力码激活时，流程不得安装为可运行
状态；说明该前置条件并让用户联系开发者购买能力码、自行完成激活。不得在流程、脚本、日志或结果中保存能力码，
也不得尝试绕过限制。

会改变页面状态的导航、点击、填写、下载、滚动和按键仍需操作前观察与操作后验证。结构化 DOM
结果可以参与定位和读取，但隐藏元素不能伪装成当前可见屏幕对象；关键结果优先用重新定位、重新读取
或屏幕证据交叉验证。组件缺失、浏览器缺失、会话失效或前台验证受系统限制时明确停止，不退化为
猜坐标或普通 Profile 操作。

### Agent 接管与步骤级操作授权

动态步骤可以声明 `执行者：agent`，并在基本信息声明 `引擎能力：agent-checkpoint@1`：

```markdown
### 判断或操作当前页面

- 执行者：agent
- 指令：确认当前页面状态，并按流程目标处理唯一目标
- 请求观察：截图、OCR、UI 元素
- 允许操作：屏幕操作
- 结果格式：completed=BOOLEAN
- 超时：120 秒
- 失败：停止
```

`请求观察` 必填，但只描述允许按需读取的观察类型，不能解释为操作授权。`允许操作` 可省略；
当前只登记 `屏幕操作`，省略时 Agent 不得改变屏幕。步骤还必须声明结果格式、有限超时和失败策略，
不能同时包含固定 `动作`、条件分支、有界重复或新窗口登记。

DSH Provider 只有在兼容插件能够证明任务级工具过滤时才可接受 `屏幕操作`。`dsh-screen-automation`
0.1.6 源码已提供策略版本和精确白名单的执行时校验；在兼容版本完成发布、安装和连接验证前，
Provider 仍默认拒绝真实屏幕操作，不得靠提示词、手工环境变量或未经验证的版本号冒充权限隔离。
同一 Provider 递归触发 checkpoint 时会返回 `recursive_agent_call`，流程应停止并让用户重新设计
边界，不得自动重试。

Provider 能力必须在运行时探测。本平台 中安装本 Skill，只证明 Agent 可以主动调用小助手，
不证明小助手具备反向创建 本平台 任务的授权。外部 Provider 不可用时，可以使用平台明确报告
为可用的小助手官方智能服务；免费版、专业版、组件未安装、未授权和平台不支持必须分别解释。

Windows 与 macOS 用户都通过“设置 → Agent 接入”管理自动分派。连接测试后至少运行一次只读 Agent 步骤，
确认 checkpoint 经 Provider 返回严格结果并恢复流程；不得把 Provider 版本探测成功当作纵向闭环。

### 填写表单与运行期锚定

`填写表单` 用顿号分隔多个 `字段标签=值`。默认逐个以字段标签进行 OCR 定位；当输入框没有
可识别的占位文字、或 macOS 不适合依赖 Tab 顺序时，为每个字段写运行期定位修饰：

```markdown
- 动作：填写表单：锚定【用户称呼（选填）】偏移【0,42】用户称呼=演示用户、锚定【手机号（选填）】偏移【0,42】手机号=13800000000、锚定【请用一句话概括问题或建议】反馈标题=示例标题、锚定【建议写明使用场景】建议内容=示例正文
```

- `锚定【OCR文字】`：在当前操作区域内实时 OCR 查找该文字；可用框内占位文字，也可用输入框
  上方或旁边的稳定标签。
- `偏移【x,y】`：只可紧接 `锚定` 使用，表示从 OCR 文字中心向右/向下的相对像素偏移，用于
  从标签点入空输入框；不是固定屏幕坐标。必须先在真实页面确认偏移仍落在输入框内。
- `相对【OCR文字】右侧`（也可为左侧、上方、下方）：只可紧接 `锚定` 使用；在同一轮 OCR
  结果中选择与参照文字符合该方位的最近候选，用来消除“手机号”等在说明文字和字段标签中重复
  出现的歧义。例如：`锚定【手机号】相对【用户称呼】右侧偏移【0,42】`。
- `点【名称】`：使用已声明的命名点直接点击该字段；同一字段不能同时使用 `点` 和 `锚定`。
- `焦点文字【文字】`、`焦点点【点名称】` 与 `按序连填` 是整个表单的可选方式；`按序连填`
  依赖系统 Tab 焦点移动，macOS 上优先逐字段使用 `锚定`/`偏移`。

不得省略锚定而单独写 `偏移` 或 `相对`，不得为同一字段重复声明锚定、相对定位或偏移。运行时每个锚定都会重新
OCR；偏移点超出操作区域上下边界时，底座最多滚动 3 次，并在每次滚动后重新读取操作区域、重新
OCR 锚定。横向越界、锚点消失或仍然越界都会安全停止。不得把“滚动一下试试”写成无上限循环，
不得为了绕过停止而改成操作区域外的固定坐标。每次锚定成功后，底座会在实际 OCR 命中的文字框
上短暂显示虚线提示；用户应借此确认匹配到的是正确字段，再继续使用该流程。

## 交互模板

交互模板与交互锁共享“交互”前缀，是命名上的一对呼应概念，但机制上各自独立：交互锁协调多个
自动化流程，避免在弹菜单、确认等窗口期间互相插入操作；交互模板把“打开菜单→识别菜单项→点击→
必要时确认”这类连续交互，打包成一段由底座执行的复用事务。二者按需使用，并非强制配对。

何时使用：需要把一段连续交互打包为可复用动作、避免在 `workflow.py` 中重复实现时，用交互模板；
需要保护临时菜单/确认框窗口期不被其他流程插入时，声明交互锁；单一动作（点击、输入、滚动）
直接用动作命令。首期交互模板只有 `上下文菜单操作`，章节标题必须写成 `上下文菜单操作【名称】`：
字段以本文件为准，也可用 `cli workflow schema templates` 输出当前引擎的权威字段清单。

```markdown
## 交互模板

### 上下文菜单操作【复制文章链接】

- 打开方式：右键
- 目标：点【文章菜单位置】
- 菜单区域：区域【文章快捷菜单】
- 菜单项文字：复制链接
- 等待菜单出现：DURATION(0.8s)
- 菜单未出现时：停止
- 确认：无需确认
```

字段只允许 `打开方式`、`目标`、`菜单区域`、`菜单区域2`、`菜单项文字`、`等待菜单出现`、`菜单未出现时`、`确认`、
`确认区域`、`等待确认出现` 和 `长按时长`。`打开方式` 只能是 `右键` 或 `长按`；`确认` 可写
`无需确认`，也可写 `点击文字【删除】` 或用顿号声明备选文字，如 `点击文字【删除、确认】`。
确认按钮名称需要由用户或运行环境调整时，写成 `点击参数【确认按钮文字】`；参数值同样可以用顿号
提供多个候选名称。
需要确认时必须声明 `确认区域`，可引用具名区域、使用带锚点的 `RECT(...)`，或使用
`PERCENT_RECT(...)`。只有在该区域识别到声明文字后才会点击；没有识别到则停止，禁止盲点。
模板名称不得重复，目标、菜单区域与具名确认区域必须属于同一操作区域。
`等待菜单出现` 与 `长按时长` 必须是 `DURATION(...)`，也可以写裸值（如 `0.8s`、`1.2s`）或 `参数【名称】` 交给用户校准；
两者省略时分别按 `DURATION(0.5s)` 和 `DURATION(1s)` 处理，`菜单未出现时` 省略时按 `停止` 处理。
`菜单项文字` 既可以直接写文字，也可以写 `参数【名称】`；运行时会读取该参数的当前值后再进行 OCR。
菜单文字也可以和确认按钮一样用顿号提供多个候选，例如 `菜单项文字：删除该聊天、删除会话`；运行时按
候选顺序识别，命中最先出现的文字。需要让用户或不同环境调整菜单名称时，应优先使用参数引用。
菜单可能向上弹出时，可增加 `菜单区域2` 声明第二个候选区域；底座先识别 `菜单区域`，未命中再识别
`菜单区域2`，两个区域必须属于同一操作区域。

动态列表行允许把模板目标和菜单区域直接写成带锚点的表达式，例如：

```markdown
- 目标：POINT(x=AREA_CENTER_X,y=ROW_Y)
- 菜单区域：RECT(left=AREA_CENTER_X,top=ROW_Y-33,right=AREA_RIGHT,bottom=ROW_Y+392)
```

这种模板必须由程序扩展在识别出当前行后调用，并传入本次运行的行锚点：
`ctx.templates.context_menu("删除当前对话", anchors={"ROW_Y": center_y})`。`AREA_CENTER_X` 是当前操作区域的
水平中心，由底座自动计算，因此长按点会保持原流程的水平位置。
`ROW_Y` 是当前处理行的 Y 基准；没有当前行上下文时不得猜测或复用旧值。纯 Markdown 步骤调用不会自动产生
`ROW_Y`，因此不能直接执行依赖 `ROW_Y` 的模板。

步骤中用 `动作：执行交互模板【复制文章链接】` 调用，程序扩展中用
`ctx.templates.context_menu("复制文章链接")` 调用，两者共用这一份 Markdown 声明。打开菜单、
识别菜单、选择菜单项和验证由底座包成一段交互事务，其他流程不会插入其间。

### Python 调用交互模板的契约

`ctx.templates.context_menu(name, anchors=...)` 使用与 Markdown 同一份模板声明：

- `anchors` 提供本次运行需要的动态锚点，例如 `{"ROW_Y": center_y}`；`AREA_LEFT`、
  `AREA_TOP`、`AREA_RIGHT`、`AREA_BOTTOM`、`AREA_CENTER_X` 由底座按模板操作区域自动补齐。
  模板引用了 `ROW_Y` 或自定义锚点而调用方未提供时，会抛出明确错误，不会静默使用错误坐标。
- `参数【名称】` 在运行时会从流程参数（`ctx.config`）解析；也可以直接写固定文字。
- 坐标表达式支持 `参数【名称】` 作为 x/y 分量，例如 `POINT(x=参数【行中心X】,y=ROW_Y)`，
  参数值是数字或标准锚点表达式；也允许调用方通过 `anchors` 传入自定义锚点名。
- 调用会自动包成交互事务，默认等待 30 秒，开始/结束说明使用模板名；需要与规则中声明的
  `交互锁开始`/`交互锁结束`/`等待交互锁` 对齐时，可传
  `start=rule["交互锁开始"], end=rule["交互锁结束"], timeout=ctx.values.duration(rule["等待交互锁"])`。
- 成功返回 OCR 命中的菜单项对象（含 `center`、`box`、`text`、`confidence`），有确认框时
  额外带 `confirmation`；菜单项或确认按钮未识别到时抛出 `ScreenStateMismatch`，模板未声明时
  抛出 `WorkflowFatalError`。

## 条件、重复、恢复和输出

- 条件：`变量【名称】` 与参数、变量、数字或 `【文字】` 比较。
- 运算：为空、不为空、等于、不等于、包含、大于、大于等于、小于、小于等于。
- 分支动作：设置变量、跳到步骤、停止流程。
- 重复：必须同时声明目标步骤、“直到”条件和大于 0 的最大次数。
- 失败策略：等待、有限重试、重新选择、询问用户、跳过当前步骤或停止。
- `保存为：变量【名称】` 保存步骤结果；`输出` 逐字段绑定当前时间、变量、参数或文字常量。
- 有输出必须声明“保存结果”权限。

## 规则与程序扩展

参数 = 每次运行可能需要校准的“旋钮”（等待时长、次数、按钮位置、偏移、颜色值）；规则 = 流程作者
一次定义好、描述目标软件业务事实的配置（区域映射、分类标签、菜单动作、循环策略）。判定标准：
每次运行可能要改的 → 参数；流程作者定义一次、稳定不变的业务事实 → 规则。
规则是流程包自己的可读配置。复杂的重复界面模式可增加一个受限的 `workflow.py`：

```markdown
## 规则

### 规则名称

- 区域：区域【统计区域】
- 标签：今日=today；本周=week

## 程序扩展

- 文件：workflow.py
- 入口：run
- 用途：按上述规则读取统计区域。

## 流程

### 执行规则

- 动作：执行程序扩展
- 逐项输出：是
```

应用名称、文字、坐标、HSV、分类、菜单动作和循环策略必须保留在流程包的声明（参数或规则）中；
平台代码只提供公共原子能力。程序扩展只能使用 `ctx` SDK，不能直接调用屏幕/系统库。逐项输出使用
`当前结果【字段】` 绑定输出。影响数据的流程通过步骤观察、最终确认和失败策略控制风险；不要用强制人工选窗替代唯一候选自动确认规则。

程序扩展必须使用以下形态：

```python
def run(ctx):
    rule = ctx.manifest["flow"]["task_rules"]["规则名称"]
    ctx.stop.check()
    # 只通过 ctx.ocr、ctx.screen、ctx.geometry、ctx.window、ctx.mouse、ctx.browser 等公共能力工作
    yield {"result": "可序列化结果"}
```

必须遵守：

- 入口函数是 `run(ctx)`，返回 `dict`、可迭代的 `dict` 或 `None`；
- 每轮循环调用 `ctx.stop.check()`，循环次数从 `workflow.md` 读取并有上限；
- 鼠标键盘组合动作放在 `ctx.input.transaction()` 中；
- 影响界面的动作使用 `ctx.step.perform()` 并以重新读屏作为成功条件；成功条件不得恒为 `True`；
- 需要用户观察的节点使用 `ctx.debug.step()`；
- 可调点、区域、颜色、文字、正则、分类、菜单名称、等待和上限从规则读取；
- 不导入或直接调用屏幕、窗口、网络、子进程和操作系统控制库；
- 失败时关闭本流程打开的辅助窗口，但不得关闭无法唯一确认的其他窗口。

临时菜单或确认框必须声明并实现交互事务：

```markdown
- 交互锁开始：打开快捷菜单之前
- 交互锁结束：确认框关闭之后
- 等待交互锁：DURATION(30s)
- 菜单验证超时：DURATION(6s)
```

能用交互模板表达的场景优先使用交互模板，底座已把“打开—识别—选择—确认”包成交互事务；
只有模板表达不了的自定义交互，才在程序扩展中手写交互锁字段并传给 `ctx.input.transaction`。

交互锁只协调多个自动化流程，不锁住用户本人。开始和结束必须成对写入 `workflow.md`，并作为
`start`、`end` 参数传给 `ctx.input.transaction`；SDK 在进入和退出真实事务时记录它们。
`等待交互锁秒数` 只限制排队时间，不会定时解锁。事务持有时间由真实代码边界及内部有限验证超时
限制。只读识别和普通等待不得包在长事务中。同一截图区域需要匹配多个候选文字时，必须一次 OCR
后在内存中匹配全部候选，禁止为每个候选文字重复截图。

## 权限

登记名称：读取屏幕、点击屏幕/操作鼠标、操作键盘、读取剪贴板、写入剪贴板、读取文件、
保存结果/写入文件、控制应用、读取浏览器、操作浏览器、浏览器下载、管理浏览器会话。
只声明最低权限，但不能少于真实动作需要的权限；任何浏览器权限都必须同时声明
`browser-enhancement@1`。

## 开发和验收

1. 先确认目标、完成标志、禁止动作、输出和失败边界。
2. 验证启动窗口规则：唯一候选自动确认；多个候选显示虚线框由用户选择。
3. 先验证只读识别，再模拟运行，再由用户监督一次安全操作。
4. 测试一条数据、停止、重试、重新选择、跳过和最大循环边界。
5. 安装前运行 `health -Target <流程标识>`，首次真实运行由用户监督。
6. 向用户展示真实自然语言步骤、权限、输出、测试范围和回退方式。

## `inspect`、`validate` 和真实验收

开发副本完成后依次运行：

```powershell
& $AppCli cli workflow inspect <流程包目录>
& $AppCli cli workflow validate <流程包目录>
```

校验会检查：

- Markdown 章节、字段和中文命令是否属于当前语言；
- 标识、语义版本、坐标边界和具名引用是否有效；
- 动作使用的权限是否已经声明；
- 修改页面的步骤是否有操作前观察和操作后验证；
- 条件、循环、重试和失败策略是否有合法边界；
- 程序扩展文件、入口、导入、`ctx` 权限及危险调用是否合规；
- 输出是否有稳定字段并声明保存结果权限。

校验不会检查目标软件当前版本、坐标是否落在真实按钮上、HSV 是否准确、文字是否能被当前截图识别，
也不会证明完整业务流程已经成功。这些只能通过只读观察和用户监督的真实页面运行验收。

## 本平台 交付前逐项复核

1. 从头读取一遍生成的 `workflow.md`，确认普通用户能说出每个步骤做什么。
2. 搜索 `workflow.py` 中的数字、字符串和正则；凡是可调业务值都迁回 `workflow.md`。
3. 搜索每个 `ctx.mouse`、`ctx.keyboard` 调用，确认前置页面状态和操作后验证都存在。
4. 搜索 `while` 和 `for`，确认停止检查、业务结束条件和最大次数都存在。
5. 故意制造一次目标缺失、文字未识别和窗口关闭，确认流程会等待、重新选择、跳过或停止。
6. 提升版本，安装开发副本，保留上一版本备份，再由用户监督一条真实数据。

当前稳定 v2 允许流程包根目录中一个显式声明并通过权限/源码校验的 Python 扩展。只有跨流程公共
能力才进入 SDK；具体软件的页面判断、分类和步骤组合留在流程包。新公共能力仍需先升级平台 SDK、
编译器、运行器和本标准。
